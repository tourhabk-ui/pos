# Сейсмо-реле — доставка Telegram-каналов КБГС и EQKam по расписанию

## Задача

КБГС РАН и EQKam живут в Telegram. `t.me` для нашего хостинга (Timeweb, РФ)
гео-закрыт, поэтому страницы каналов тянет **тот, кто снаружи**, и POST-ит их
на `/api/cron/safety-ingest`.

До сих пор этим занимался раннер GitHub — и делал бы это хорошо, если бы
приходил вовремя. Замер 29.08: планировщик GitHub доставляет **1-4%**
запрошенного (`safety-ingest` просит 288 прогонов в сутки, получал 2-4).
Отсюда в отчётах Watchdog «Сейсмо-канал Telegram отстаёт: 104 мин при норме 5».

## Почему не помогают решения, которые помогли остальным

| Что | Почему не подходит |
|---|---|
| Супервизор контейнера (`start.js`) | зовёт наш же эндпоинт — фетч всё равно уйдёт с прода, в ту же стену |
| Внешний планировщик (cron-job.org) | дёргает наш адрес — то же самое |

Нужен не «кто вовремя позовёт», а **кто сам сходит за страницей снаружи**.
Раннер это умеет, но приходит когда захочет. Воркер Cloudflare приходит по
расписанию и живёт вне РФ.

## Чего мы не знаем заранее — и как это проверить

В соседнем `infra/ai-relay/` записан урок, оплаченный временем: рассуждение
«воркер вне РФ, значит блокировка обойдена» оказалось **ложным** для
OpenRouter. Тот сам стоит за Cloudflare, и субзапрос воркера доносил наверх
`CF-Connecting-IP` исходного клиента — блокировка следовала за звонящим, а не
за путём.

Здесь случай другой по двум причинам: Telegram держит свою инфраструктуру и за
Cloudflare не стоит, а у cron-триггера нет исходного клиента вовсе — запрос
порождает сам Cloudflare. **Но это рассуждение, а не замер.**

Поэтому первым делом — `/selftest`, который ходит за теми же адресами и
возвращает размеры ответов, ничего не отправляя на прод:

```bash
curl -H "Authorization: Bearer <CRON_SECRET>" \
     https://vedar-safety-relay.<account>.workers.dev/selftest
```

```jsonc
{
  "census": {
    "kbgsras_html": "184213 байт",   // байты есть — блокировка обойдена
    "eqkam_html":   "отказ: HTTP 403" // отказ — путь не работает
  },
  "would_post": true
}
```

Пока `/selftest` не показал байты, считать задачу решённой нельзя.

## Деплой

```bash
cd infra/safety-relay
npx wrangler secret put CRON_SECRET   # то же значение, что в переменных Timeweb
npx wrangler deploy
```

Секрет задаётся именно `secret put`, а не в `[vars]`: содержимое `vars` видно
в панели и уезжает в конфиг.

## Что остаётся как было

**Воркфлоу `cron-safety-ingest.yml` не снимается.** Он остаётся независимой
конечностью: если воркер встанет или Cloudflare начнёт получать отказ, путь
сохранится — пусть и с прежней частотой.

Дубли при этом безопасны **по построению**: раннер и так каждые пять минут
шлёт страницу канала целиком и заново, значит дедуп на приёмнике существует с
первого дня — иначе дубли пошли бы сразу. Воркер шлёт то же самое тем же
путём и теми же id (извлечение постов MAX повторено, а не улучшено, именно
ради совпадения id).

## Что делает воркер

Каждые 5 минут забирает и отправляет одним телом:

| Поле | Источник | Обязательно |
|---|---|---|
| `kbgsras_html` | `t.me/s/kbgsras` | да |
| `eqkam_html` | `t.me/s/eqkam` | да |
| `minec_html` | `t.me/s/minec_tourism` | нет |
| `kamgov_xml` | три пути RSS `kamgov.ru` | нет |

**Канала МЧС в MAX здесь нет намеренно.** Первая версия тянула и его — вместе
с копией извлечения постов из HTML, скопированной из воркфлоу ради совпадения
id (на них держится дедуп). Копию завернули сторожа `html-text` и
`html-entities`, и по делу: вместе с логикой копировался её дефект.

Чинить только в воркере было нельзя — id разошлись бы с раннером, и один пост
приехал бы дважды под разными именами; в канале МЧС это второй наряд по одному
сообщению. Чинить в обоих местах — отдельная работа про MAX, а не про
опоздание сейсмо-канала. Поэтому MAX целиком остался у раннера: одна копия
парсера лучше двух.

Если обязательного канала нет — **POST не отправляется вовсе**. Приёмник
вернул бы 400, и в журнале осталась бы «ошибка сервера» вместо правды
«Telegram не отдал страницу».
