## Конвенции этого репо (обязательно соблюдать)

- Тесты лежат в `tests/unit/*.test.ts`, запуск — `npx vitest run` (не `tests/setup.ts` — этот файл не подключён, реальный конфиг в `vitest.config.ts` использует `test/setup.ts`, единственное).
- Для роутов/сервисов, читающих БД — мокай `@/lib/db-pool` (`import { pool } from '@/lib/db-pool'`) или `@/lib/database` (`import { query } from '@/lib/database'`) в зависимости от того, что реально импортирует файл. Смотри соседние тесты (`tests/unit/*.test.ts`) на актуальный паттерн мока перед тем как писать новый — не выдумывай свой.
- Если тестируешь SQL-запрос — проверь реальные имена колонок по `migrations/*.sql`, а не по тому, что кажется логичным. В этом репо уже были баги из-за обращения к несуществующим колонкам (`operator_tours.duration_days` вместо `multi_day_count`, и т.п.) — не повторяй имя колонки бездумно, свери с CREATE TABLE/ALTER TABLE.
- Логика безопасности/SOS — если код трогает `location_safety_profile`, `external_alerts`, MChS-алерты и т.п., добавь тест на «не должно тихо терять предупреждение» (fail-open предпочтительнее fail-silent).
- Без `any` — `unknown` + type guards.

## Шаги

1. Прочитай файл(ы) из `$ARGUMENTS` полностью, пойми, что тестировать: happy path + граничные случаи + то, что реально может сломаться (null/undefined из БД, пустые массивы, отсутствующие ключи).
2. Напиши тесты в `tests/unit/<имя-модуля>.test.ts` (или дополни существующий файл, если он уже есть для этого модуля — не создавай дубликат).
3. Прогони `npx vitest run <путь-к-новому-файлу>` — если красный, почини (либо тест неверный, либо нашёл реальный баг — если баг реальный, скажи об этом явно, не просто подгоняй тест под баг).
4. В конце прогони `npx tsc --noEmit` и полный `npx vitest run`, чтобы убедиться, что ничего не сломал.

Не коммить и не пуш без явной просьбы — просто покажи результат (сколько тестов, что зелёное/красное).
