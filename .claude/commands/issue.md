Возьми issue #$ARGUMENTS и доведи до PR по конвейеру проекта.

## Конвейер

1. **Прочитай issue** (gh CLI или GitHub MCP `issue_read`) целиком, включая комментарии. Если постановка неоднозначна — сначала вопросы, потом код.
2. **Оцени объём** (как /scope): файлы, миграция, пересечение с §7 CLAUDE.md. Если задевает схему БД / авторизацию / API / бронирования — сначала краткий план на подтверждение (§5).
3. **Ветка от свежего main**: `git fetch origin main && git checkout -B claude/<кратко-о-задаче> origin/main`.
4. **Реализация** по конвенциям: параметризованный SQL, Zod на входы, ошибки по-русски, идемпотентные миграции (`IF NOT EXISTS`), DS-токены в UI, без эмодзи и console.log. Тесты на новую логику обязательны.
5. **Проверки**: `npx tsc --noEmit` → eslint по затронутым файлам → `npx vitest run` → `npm run build`.
6. **Draft PR**: русское «Что/Почему/Проверки», в тело — `Closes #<N>`. Крупный дифф — прогнать /code-review до undraft.
7. **CI зелёный + нет review-комментариев** → undraft → squash merge (если владелец не просил ждать).

## Правила честности

- Не выдумывай данные для сидов — чего нет в issue/коде, то NULL с комментарием.
- Если issue заблокирован внешним (секрет, сеть, человек) — скажи об этом сразу, сделай незаблокированную часть и явно перечисли, что осталось.
