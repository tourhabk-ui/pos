Собери фичу из API и UI по одному контракту. Код пишет главная сессия; параллельно идёт только чтение.

> До 13.11 эта команда запускала двух помощников, которые писали API и UI
> одновременно. Владелец привёл её к правилу CLAUDE.md §5.1: помощники читают
> и называют факты, правку делает тот, кто отвечает за неё перед владельцем.
> Параллельным остался сбор фактов для двух половин фичи.

## Аргументы

`$ARGUMENTS` — описание фичи (например: "страница финансовой сводки оператора с графиком выручки")

## Шаг 1 — Декомпозиция (сделай сам, не делегируй)

Определи и зафиксируй:

```
FEATURE: {название}
API_ROUTE:   {метод} {путь}  — e.g. GET /api/hub/finance/summary
API_TABLES:  {таблицы}       — e.g. operator_payouts, tour_payments
UI_FILE:     {путь к tsx}    — e.g. app/hub/finance/page.tsx + _FinanceClient.tsx
UI_DATA:     {что отображать} — e.g. total_earned, pending_payout, chart_data[]
CONTRACT:    {JSON-структура ответа API}
```

Контракт записывается до кода: по нему пишутся обе половины.

## Шаг 2 — Параллельное чтение

Запусти **одним сообщением** двух помощников поиска (`poisk`, Sonnet, только
чтение). Каждый возвращает факты с адресом `file:line`, а не код.

### Помощник A — данные для API

```
Нужны факты для роута {API_ROUTE}. Только чтение, ничего не правь.

1. Колонки и типы таблиц {API_TABLES}: по docs/DB_SCHEMA.md и migrations/.
   Назови точные имена колонок, которые нужны для {CONTRACT}; каких нет — скажи.
2. Ближайший по смыслу существующий роут в той же роли: адрес и чем он
   проверяет вход (requireAuth / requireAdmin / requireRole, проверка владения).
3. Сторожа, которые заденет новый роут (реестр публичных роутов, перепись
   роутов, сторожа ПД и денег): имена файлов в tests/unit.

На каждый пункт — «есть» с адресом, «нет» (чем искал) или «не смог посмотреть».
```

### Помощник B — данные для UI

```
Нужны факты для страницы {UI_FILE}. Только чтение, ничего не правь.

1. Ближайшая по смыслу существующая страница той же роли: адрес page.tsx и
   клиентского компонента, как она грузит данные и показывает загрузку,
   ошибку и пустоту.
2. Где роль регистрирует пункт навигации (сайдбар, меню) — адрес.
3. Какие ds-классы и компоненты уже используются для того, что надо показать
   ({UI_DATA}): карточки, таблицы, графики.

На каждый пункт — «есть» с адресом, «нет» (чем искал) или «не смог посмотреть».
```

Факты, от которых зависит безопасность, деньги или ПД (проверка владения,
какие поля отдаются другой роли), перечитай по коду сам: помощник называет
адрес, решает главная сессия.

## Шаг 3 — Код (главная сессия)

Сначала API, потом UI.

**API — что обязано быть:**
- `import { pool } from '@/lib/db-pool'` (named, не default)
- JWT через `requireAuth` / `requireAdmin` / `requireRole` из `lib/auth/middleware.ts`
- Zod-валидация входных данных
- параметризованный SQL (`$1, $2`), без конкатенации
- `FROM operator_bookings` (не `FROM bookings`), поле `booking_status` (не `status`)
- `FROM operator_tours` (не `FROM tours`)
- ошибки — понятные сообщения на русском; отказ базы — 500 с записью в лог, а
  не пустой успешный ответ
- тип ответа — {CONTRACT}

Защищённые зоны (`middleware.ts`, `lib/auth.ts`, `app/api/payments/`,
`app/api/safety/sos`; полный список — `scripts/protected-zones.mjs`) без слова
владельца не правятся.

**UI — что обязано быть:**
- цвета только через CSS-токены: `var(--accent)`, `var(--ocean)`, `var(--bg-card)`,
  `var(--text-primary)`, `var(--text-secondary)`, `var(--border)`
- DS-классы: `ds-card`, `ds-page`, `ds-btn`, `ds-btn-primary`, `ds-h1`, `ds-h2`,
  `ds-label`, `ds-badge`
- заголовки — `font-[family-name:var(--font-playfair)]`, остальное Outfit
- иконки — только `lucide-react`; эмодзи и хардкод hex запрещены; `bg-white` и
  `text-white` — не на сплошном фоне
- стекло (`backdrop-blur`) — только поверх фото, карт и тёмных подложек; на
  светлом сплошном фоне, у SOS и у подтверждений его нет (CLAUDE.md §2)
- `page.tsx` — серверный компонент с `metadata`; `_FeatureClient.tsx` —
  `'use client'`, вся логика и `fetch({API_ROUTE})`
- загрузка — `ds-skeleton`; ошибка — текст на русском и `ds-btn-secondary` для
  повтора; пустота — честная строка, не заглушка

## Шаг 4 — Проверка

1. Типы совпадают: CONTRACT из API ↔ то, что читает UI.
2. Путь `fetch` в UI совпадает с настоящим API_ROUTE.
3. `npx tsc --noEmit` — 0 ошибок.
4. Тест на роут вызовом и на экран рендером (CLAUDE.md §4, «Сторож судит
   поведение»); SQL нового запроса — на настоящей базе (скилл `pg-verify`).
