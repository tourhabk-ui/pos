Построй фичу через red-green-refactor: $ARGUMENTS

## Цикл

1. **Red** — напиши тест(ы) в `tests/unit/<модуль>.test.ts` на поведение, которого ещё нет. Прогони `npx vitest run <файл>` — убедись, что тест реально падает (не падает по опечатке в самом тесте, а именно потому что фичи нет).
2. **Green** — напиши минимальный код, чтобы тест прошёл. Не добавляй ничего сверх того, что требует тест — никаких «на будущее».
3. **Refactor** — когда тест зелёный, почисти код (убери дублирование, вынеси общее), не меняя поведение. Перепрогони тесты после каждого рефактор-шага.
4. Повтори цикл для следующего кусочка поведения, пока фича не покрыта целиком (happy path + граничные случаи).

## Конвенции этого репо

- Тесты — `tests/unit/*.test.ts`, `npx vitest run`. Моки БД — `@/lib/db-pool` (`pool.query`) или `@/lib/database` (`query`), смотри соседние тесты на актуальный паттерн перед тем как писать новый мок с нуля.
- Zod-валидация на входе API route — это часть фичи, не «потом»: пиши тест на невалидный инпут сразу в Red-шаге.
- SQL — только параметризованный (`$1, $2`). Если тест бьёт по реальным именам колонок — сверь их с `migrations/*.sql` (`CREATE TABLE`/`ALTER TABLE ADD COLUMN`), не угадывай.
- TypeScript strict — `unknown` + type guards, без `any`, даже во временном Red-коде.
- `npx tsc --noEmit` должен быть чист на каждом Green-шаге, не только в конце.

## Когда остановиться

Как только все запланированные кейсы (happy path + границы, которые реально важны для этой фичи) зелёные — прогони полный `npx vitest run` и `npx tsc --noEmit`, покажи итог. Не строй абстракций под гипотетические будущие требования, которых не было в задаче.
