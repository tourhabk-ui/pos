# AI Risk Assessment — Derisking by Design (TourHab / Ведар)

> Управление рисками AI встроено в процесс с самого начала, а не «заплаткой» потом.
> Платформа безопасности туристов Камчатки: **главный риск — AI выдаёт неверный факт о безопасности → турист пострадал.** Всё остальное вторично.
> Ориентиры: NIST AI RMF, EU AI Act, OWASP LLM Top-10.

---

## 0. Риск-аппетит платформы (принято)

| Класс риска | Аппетит | Правило |
|-------------|---------|---------|
| **Выдуманный факт о безопасности** (опасность, статус места, проходимость, МЧС) | **НОЛЬ** | Лучше «не знаю», чем выдумка. Только из инструментов/БД. |
| Выдуманные коммерческие данные (цена, наличие, скидка в КП клиенту) | **НОЛЬ** | Только из БД/переданных туров. |
| Галлюцинация в описании места/маршрута (числа, координаты) | низкий | Нет данных → обобщённо, без выдуманной конкретики. |
| Утечка секретов/PII в логи/ответы | **НОЛЬ** | Секреты только из env; PII не логировать. |
| Автоправка кода без ревью (Evo) | низкий | Не трогать auth/payments/SOS/схему БД; tsc+тесты обязательны. |
| Тон/стиль/вода | средний | Допустимо, не блокер. |
| Латентность/стоимость AI | средний | Мониторить, не блокер. |

## 1. ЧЕК-ЛИСТ ДЛЯ AI-АГЕНТА (заполнять перед мержем агента/промпта)

Применять к: Кузьмич, Watchdog, Editor, Scout-Innovator/Digest, Evo (growth/evolution/feedback), danger-analyst, lead-processor, places/kuzmich-enricher, execution-handlers.

### A. Анти-галлюцинация (критично)
- [ ] Промпт **запрещает выдумывать** факты, которых нет во входных данных (явное правило «нет данных → null / "не знаю"»)
- [ ] Факты о безопасности берутся ТОЛЬКО из инструментов/БД (`get_guardian_context`, safety_profile), не из памяти модели
- [ ] Числа (цены, высоты, координаты, даты, расстояния) — только из источника, не «на глаз»
- [ ] Для клиентских артефактов (КП в PDF, посты) — запрет на выдуманные цены/скидки/обещания
- [ ] Закрытые перечни (activity_types, категории) — «только из списка, не изобретать»

### B. Источник правды
- [ ] Агент читает из канонических таблиц: `places` / `kamchatka_routes` / `operator_tours` / `operator_bookings` (не устаревшие, не `agent_route_knowledge` на запись)
- [ ] SQL параметризован (`$1,$2`), `import { pool }`, явные колонки
- [ ] Внешние факты (web/RSS) НЕ смешиваются с фактами безопасности

### C. Guardrails и деградация
- [ ] Внешние вызовы (AI, Telegram, U-ON, БД) в try/catch — сбой не валит основной поток
- [ ] AI только через `callAIWaterfall()` / `callAIFast()` (не прямые провайдеры)
- [ ] Таймаут + retry на нестабильный egress (Telegram/внешние API)
- [ ] При пустом/невалидном ответе AI — не сохранять мусор (проверка длины/схемы)
- [ ] Структурный вывод — через Zod-схему или строгий JSON-парс с фолбэком

### D. Human-in-the-loop / границы автономии
- [ ] Необратимые действия (правка кода, рассылка, постинг) — либо ревью человека, либо жёсткие ограничения (PROTECTED_PATHS, не трогать auth/payments/SOS)
- [ ] Агент НЕ обещает того, что не сделано системой («связался с оператором», «100% мест»)
- [ ] Экстренные сценарии (SOS/ЧП у Кузьмича) → сразу 112/МЧС, без воды и допвопросов

### E. Audit trail и наблюдаемость
- [ ] Действия логируются в `ai_actions_log` / `agent_run_history` с правильным `action_type` (метрики должны совпадать с тем, что реально пишется!)
- [ ] Латентность и ошибки внешних вызовов логируются (как `uon_sync_log`)
- [ ] Есть health-метрика, читающая РЕАЛЬНЫЕ типы событий (см. урок: ложное «Кузьмич молчит» из-за расхождения action_type)

### F. Верификация перед мержем
- [ ] `npx tsc --noEmit` → 0 ошибок
- [ ] `npx vitest run` → зелёные
- [ ] `audit.mjs --staged` → 0 нарушений CLAUDE.md
- [ ] Прогон агента вживую (или smoke-test) — проверить, что в БД реально что-то изменилось, а не `{improved:5}` при нуле (урок «тихих ошибок»)

## 2. ФОРМАЛЬНАЯ ОЦЕНКА РИСКОВ (NIST AI RMF + EU AI Act + OWASP LLM)

Заполняется на **новую AI-фичу/агента** на этапе Design.

### Паспорт фичи
| Поле | Значение |
|------|----------|
| Фича/агент | _________ |
| Владелец риска (AI Risk Owner) | _________ |
| Дата оценки / ре-оценки | _________ |
| Класс по EU AI Act | minimal / limited / **high-risk** (безопасность людей = high) |
| Автономность | suggest-only / human-approved / **autonomous** |
| Обратимость действий | обратимо / необратимо |

### Матрица рисков (вероятность × ущерб = приоритет)
| OWASP LLM | Риск | Вероятн. | Ущерб | Митигация (из чек-листа §1) | Остаточный риск |
|-----------|------|----------|-------|------------------------------|-----------------|
| LLM09 Misinformation | Выдуманный факт безопасности | сред. | **критич.** | §A: запрет выдумки, только инструменты; §D: SOS-триггер | низкий |
| LLM09 | Выдуманная цена/обещание клиенту | сред. | высок. | §A: только из БД; fallback без обещаний | низкий |
| LLM01 Prompt Injection | Внешний текст (RSS/TG/отзыв) перехватывает агента | сред. | сред. | §B: не смешивать внешнее с safety; валидация | средний |
| LLM02 Sensitive Disclosure | Утечка ключа/PII | низк. | высок. | §C: секреты из env, PII не логировать | низкий |
| LLM06 Excessive Agency | Авто-правка ломает прод | сред. | высок. | §D: PROTECTED_PATHS, tsc+тесты, не трогать auth/pay/SOS | низкий |
| LLM04 Data/Model Poisoning | Мусор из скрейпа в БД знаний | сред. | сред. | §A/§B: только явные факты, дедуп, проверка длины | средний |
| LLM05 Improper Output | Невалидный JSON/HTML ломает поток | сред. | низк. | §C: Zod/строгий парс + фолбэк | низкий |
| — Operational | Тихий сбой (агент рапортует успех при нуле) | сред. | высок. | §F: smoke-test, проверка реальных изменений в БД | низкий |
| — Operational | Сломанная health-метрика (ложная тревога) | сред. | сред. | §E: метрика читает реальные action_type | низкий |

### Решение
- [ ] **GO** — остаточные риски в рамках аппетита
- [ ] **GO с условиями** — _________ (напр. только suggest-only до накопления данных)
- [ ] **NO-GO** — неприемлемый остаточный риск

## 3. Процесс (организационно)

- **AI Risk Owner** — Owner (единоличный decision-maker, см. AGENTS.md).
- **Risk Review на старте** — обязателен для фич, затрагивающих: безопасность туриста, авторизацию, платежи, клиентские артефакты, автоправку кода.
- **Guardrails** — встроены в промпты (см. усиленные промпты агентов, июнь 2026) + технические (PROTECTED_PATHS, requireAuth, rate-limit).
- **Red Teaming** — раз в квартал: попытаться заставить Кузьмича выдать ложную опасность / выдуманную цену / проигнорировать SOS.
- **Incident Response** — при инциденте: 1) откатить/отключить агента, 2) зафиксировать в `agent_run_history`, 3) добавить кейс в Red Team набор.
- **Audit Trail** — `ai_actions_log`, `agent_run_history`, `uon_sync_log`, health-эндпоинты `/api/health/*`.

## 4. Быстрый старт (MVP внедрения)
1. Принять §0 (риск-аппетит) и §1 (чек-лист агента) как обязательные в PR-процессе.
2. Для каждой новой AI-фичи — §2 (паспорт + матрица) в описании PR.
3. Базовые guardrails в промптах (анти-галлюцинация, SOS-триггер) — уже внедрены.
4. Логировать критичные действия с правильным action_type; health-метрика читает реальные типы.
5. Квартальный Red Teaming Кузьмича и danger-analyst (apex-риск — выдуманная опасность).
