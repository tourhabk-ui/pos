# Персональные данные

Утечка ПД находилась на платформе уже несколькими путями, и каждый раз
не там, где её ждали:

- **агентам** отдавались заявки туристов платформы — роль агента выдаётся
  самостоятельной регистрацией, то есть любому (закрыто 26.09,
  `agent-leads-closed`);
- **публичная карточка жилья** отдавала email каждого автора отзыва
  (закрыто 26.09, `stay-review-no-pd`);
- **инструмент AI** возвращал строку брони целиком — имя, почта и пожелания
  туриста уезжали в зарубежную модель результатом, а не промптом
  (`sdk-tool-pii`);
- **форма брони гостя** собирала контакты без согласия (`pd-consent-registry`).

## 1. Три вопроса к каждому полю

Для каждого поля ответа, письма или сообщения:

1. **Кто получит?** Аноним, любой зарегистрированный, конкретная роль, сам
   человек, администратор.
2. **Нужно ли ему это поле для дела?** Не «может пригодиться» — нужно сейчас.
3. **Может ли он получить роль сам?** Турист, агент, владелец жилья, гид —
   самостоятельная регистрация. Проверка роли без проверки владения — не
   защита.

Нет ясного «да» на второй вопрос — поле не отдаётся.

## 2. Публичные ответы и страницы

- Никогда: email, телефон, полное ФИО, паспорт, дата рождения, точные
  координаты человека, `user_id` в связке с чем-то из этого.
- Имя автора отзыва — `publicReviewerName()` (`lib/reviews/public-name.ts`):
  «Имя Ф.», пусто — «Гость».
- Лишнее поле убирать из `SELECT`, а не только из ответа: не выбранное не
  утечёт при следующей правке.
- Проверка: `curl` публичного роута без токена и поиск `@`, `+7`, `email`,
  `phone` в ответе.

## 3. Данные другой роли

- Оператор видит туристов СВОИХ броней (`operatorOwnsBooking`), гид — своих
  групп через связку с оператором, агент — СВОИХ клиентов и продаж. Владение —
  через SQL-связку до `partners.user_id`, не через параметр запроса.
- Агенту по продаже через ссылку имя и ссылка туриста не показываются.
- Отказ проверки владения из-за базы — 503 и лог, а не «нет доступа» и не
  «доступ есть» (§4.0).

## 4. AI: две дороги наружу

Модели у нас зарубежные, кроме YandexGPT. ПД в модели — трансграничная
передача.
- **Промпт**: интерполяция ПД в текст — только через `redactPII()`
  (`lib/security/pii-redact.ts`) или плейсхолдер. Гард D1
  `lib/agents/compliance/pii-flow-scanner.ts` ломает сборку.
- **Результат инструмента**: строку БД модели целиком не отдавать — только
  нужные поля (`sdk-tool-pii`).
- Новый хост модели — в реестр D2 (`provider-registry.ts`) с юрисдикцией.

## 5. Письма и мессенджеры

- Всё, что ввёл человек (причина отмены, пожелания, название от оператора), —
  через `escapeHtml()` (`lib/text/escape-html.ts`); тема — `safeSubject()`.
  CodeQL 25.09 поймал причину отмены сырой в HTML письма.
- Текст чужих каналов и групп (посты операторов с телефонами) уходит в модель
  только очищенным (`group-monitor-pii`).

## 6. Сбор и согласие

- Форма, собирающая контакты человека без аккаунта, — с `PdConsentCheckbox`,
  и согласие доходит до базы (`pd-consent-registry`).
- Бронь агентом за клиента: агент не может дать согласие за клиента —
  записывается NULL («не записано»), а не выдуманное «да».

## 7. Логи

`console.error` — имя проверки и SQLSTATE, не тело строки с ПД. Не логировать
телефон и email целиком.
