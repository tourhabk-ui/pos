# Довести PR до влития

Правило владельца: **«мержи по зелёной»** — свой PR вливается сам, как только
CI зелёный. Автомерж в репозитории выключен.

## 0. До кода: сначала искать, потом писать

Слово владельца 11.11 («1»): из ponytail (MIT, github.com/DietrichGebert/ponytail)
взяты три вещи, которых здесь не было. Остальное у нас уже есть: «третий
исход» (§4.0), запрет нового движка подбора (§4), сторожа, зоны §7.

- **Куда должна дойти правка.** Прочитать задачу и код, который она задевает.
  Назвать все места: вызывающих, тесты, фикстуры, конфиг, экспорты, тексты
  агентам (MCP, A2A, llms.txt). Это и есть объём. Лишние возможности в него не
  входят.
- **Лестница.** Берётся первая ступенька, которая решает задачу целиком:
  1. нужно ли это вообще — не просили, значит нет (назвать одной строкой);
  2. уже есть в репозитории — функция, компонент, правило (`poisk`
     найдёт); использовать так, как его зовут соседи;
  3. есть в стандартной библиотеке или в платформе — Next, PostgreSQL;
  4. есть в установленной зависимости — новую ради пары строк не ставить;
  5. иначе — минимальный код, который работает.
- **Починка — в корне, один раз.** Перед правкой найти всех вызывающих
  функцию и чинить общее место, а не одного вызывающего.
- **Не режется никогда:** проверка входа на границе доверия, обработка ошибок
  от потери данных, безопасность, ПД, доступность, то, о чём просил владелец.
  Новая нетривиальная логика (ветвление, разбор, деньги, безопасность, запись
  в базу) уходит со сторожем.

## 1. До пуша

- `npx tsc --noEmit` — 0 ошибок.
- `npx eslint <изменённые файлы>` — 0 ошибок.
- Тесты изменённого и сторожа по теме (`money-path`, `pd-guard`, `pg-verify`).
- Перед PR с миграциями: `git fetch origin main` и сверка номеров — параллельные
  сессии занимают те же. Столкнулись — перенумеровать свои.
- `docs/DB_SCHEMA.md` в PR не перегенерировать — его снимает job после влития
  (`.github/workflows/db-schema-doc.yml`).
- Полный `npx vitest run`, если правка задевает общее (миграции, удаление
  роутов или сервисов, навигация).
- Перечитать свой diff глазами проверяющего: HTML из пользовательского ввода
  без `escapeHtml`, регэксп по домену без якоря, `catch` без лога.

## 2. PR

- Ветка — только назначенная сессии. Шаблон — `.github/pull_request_template.md`
  (разделы «Что изменено», «Why», Trust-First Checklist, «Проверки», «Риски»).
- В «Проверках» — числа из прогонов этой сессии, не «зелёный» по памяти.
- В «Рисках» и в отчёте владельцу последняя строка — **«Не проверено:»**:
  что пропущено или не проверено и чем это грозит. Проверено всё —
  так и написать. Строки нет — читатель решит, что проверено всё.
- Сразу после создания: подписка на события PR и отложенная проверка
  (~25 минут: полный `ci` идёт около 15).

## 3. CI

- `ci`, `kernel-pg`, `lint`, `gate`, `check`, CodeQL, «Анализ» — все должны
  быть зелёными. `review` и пропущенные `claude` не блокируют.
- **CodeQL «new alert»** — баг-репорт, а не шум. Где именно — в событии
  review comment от `github-advanced-security[bot]` (файл и строка). Случаи:
  - «Missing regular expression anchor» в тесте на домен — `toContain`
    вместо регэкспа;
  - HTML письма из введённого человеком текста — `escapeHtml`.
  Строка, которую правка лишь задела, тоже становится «новой» — чинить.
- Красное — найти причину. «Флейк» не причина. Падает и на `main` — один
  комментарий в PR с названием проверки и почему не наша.
- Перезапуск задачи сессии не дан (`rerun_failed_jobs` отвечает 403). Падение
  не наше, но тест можно сделать устойчивым — чинить в этом же PR (случай
  #3255: лимит хуков в `vitest.config.ts`). В комментарии не писать
  «перезапущено», пока перезапуск не прошёл.
- Никогда: пропускать или отключать тест, пустой коммит ради перезапуска.

## 4. Влитие

- Squash, `expectedHeadSha` — ПОЛНЫЙ 40-символьный sha головы
  (`git rev-parse origin/<ветка>`).
- После влития: отписка от PR (приходит сама), удалить свою отложенную проверку.

## 5. После влития

Влитый PR закончен. Новая работа — новая ветка с тем же именем от `main`:

```
git fetch origin main && git checkout -B <ветка> origin/main
git cherry-pick <несвязанные с влитым коммиты>
git push -u origin <ветка>
```

Ветка на GitHub после влития удаляется автоматически: `--force-with-lease`
тогда отвечает «stale info» — это не конфликт, пушить обычным `push -u`.
