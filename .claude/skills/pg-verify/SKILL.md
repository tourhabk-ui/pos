# Проверка SQL на настоящей базе

Юнит-тесты с моком `pool.query` отвечают на ЛЮБОЙ SQL. Поэтому на платформе
годами жили запросы, которые не выполнялись ни разу:
- 42P08 «inconsistent types deduced» — маяк воронки, регистрация партнёра,
  подтверждение брони жилья (`status = $1` и `CASE WHEN $1 = ...`);
- 42P10 — `ON CONFLICT (cp_transaction_id)` без предиката частичного индекса;
- `uuid = bigint` в каждом соединении кабинета гида — весь кабинет отвечал 500;
- 23514 — роль `stay` не входит в `users_role_check`, регистрация владельца
  жилья невозможна.

Во всех случаях юниты были зелёными.

## 1. Какая проверка что ловит

| Проверка | Ловит | Не ловит |
|---|---|---|
| `PREPARE` | вывод типов (42P08), несуществующие колонки и таблицы | ошибки выполнения: 42P10, CHECK, FK, уникальность |
| Выполнение в `BEGIN ... ROLLBACK` | всё, включая 42P10, 23514, 23505 | — |
| Интеграционный тест (`*.pg.test.ts`) | то же, навсегда, в CI | — |

`PREPARE` — быстрый первый фильтр. Приговор — выполнение. На прод-путь без
транзакции с откатом не ходить: пробная строка в данных — выдуманный факт.

## 2. Локальная база

Схема = baseline прода + все миграции, тем же путём, что `start.js` на деплое.
Порядок — шапка `scripts/gen-db-schema.ts`:

```
createdb schema_doc
DATABASE_URL=.../schema_doc node scripts/bootstrap-from-baseline.js
psql schema_doc -c "DELETE FROM _migrations WHERE (substring(name from '^[0-9]+'))::bigint >= 863"
DATABASE_URL=.../schema_doc npm run migrate
DATABASE_URL=.../schema_doc npm run db:schema-doc      # docs/DB_SCHEMA.md
```

Итог миграций обязан быть `Errors: 0`. База «где-то осталась от прошлого раза» —
не доказательство: если в ней уже прогонялись чужие версии миграций,
пересобрать с нуля (`DROP DATABASE` и заново).

В облачном контейнере Claude: `pg_ctlcluster 16 main start`; `DATABASE_SSL=false`.

## 3. Проверить один запрос

```sql
BEGIN;
-- подготовить данные, если нужно
PREPARE q(text, varchar) AS <запрос с $1, $2>;   -- 42P08 видно здесь
EXECUTE q('...', '...');                          -- 42P10, 23514 видно здесь
ROLLBACK;
```

Параметры без явного типа — как их шлёт node-pg (unknown), то есть `PREPARE q AS ...`
без списка типов воспроизводит прод точнее.

## 4. Интеграционный тест

- Файл `tests/integration/<имя>.pg.test.ts`, своя база (`<имя>_test`),
  поднимается из baseline + миграций, в `public` не сидит.
- Без `KERNEL_PG_TEST_URL` тест пропускается и пишет, что НЕ прогнан, а не
  зелёный.
- Запуск: `KERNEL_PG_TEST_URL=postgresql://... npx vitest run tests/integration`.
- Число pg-файлов ограничено порогом в `tests/unit/pg-tests-run-in-ci.test.ts`
  (прогон последовательный). Новый файл — порог поднимается ЯВНО, с замером
  времени и причиной в комментарии.

## 5. Сторожа формы

- `tests/unit/sql-param-cast-shape.test.ts` — реестр запросов опасной формы;
  новый запрос формы «вставь, если нет» без записи в реестре не проходит CI.
- `GET /api/cron/sql-shape-check` — `PREPARE` реестра на проде.
- `tests/unit/migration-id-type-domain.test.ts` — сверка id разных таблиц в
  миграциях только через `::text` с обеих сторон.
- `tests/unit/schema-coverage.test.ts` — таблица без `CREATE TABLE` в миграциях
  или baseline запрещена.
- `tests/unit/db-schema-doc.test.ts` — `docs/DB_SCHEMA.md` не отстаёт от
  последней миграции, менявшей схему.

Судить вывод типов статикой запрещено (CLAUDE.md §4, случай 24.08): решает сервер.

## 6. Миграция

- Номер = максимум + 1 при ЧИСЛОВОЙ сортировке:
  `ls migrations/*.sql | sed 's|.*/||' | sort -t_ -k1,1n | tail -1`.
- Перед PR — сверить с `origin/main`: параллельные сессии занимают номера.
  Столкнулись — перенумеровать свои, поправить упоминания в коде и тестах,
  пересобрать базу с нуля.
- Идемпотентна (`IF NOT EXISTS`), только вперёд.
