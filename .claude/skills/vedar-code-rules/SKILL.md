## 4. КОД

### 4.0 Третье состояние (правило владельца 19.08)

**У всякого поля и всякой проверки должен быть исход «не знаю».**

19.08 один и тот же дефект нашёлся семью способами: зелёный smoke при мёртвой
карточке; панель тревог, пустая при падающих запросах; «модель не ответила» при
успешном джобе; `rating: 4.5` у перевозчика, которого никто не оценивал;
выручка за месяц как `0.3 × общей`; выдуманный «секрет места» в посте канала;
`return true` в проверке, которая не смогла выполниться.

Формы разные, механизм один: **место, где нельзя сказать «не знаю»,
заполняется враньём.** Обязательное число — выдумывается. Обязательный
«секрет» — сочиняется. Проверка без исхода «не смог» — отвечает «хорошо».

Отсюда требования, проверяемые на ревью:

- **Тип допускает отсутствие.** `rating: number` принуждает выдумать 4.5;
  `number | null` — нет. Если поля может не быть, тип обязан это позволять.
- **У проверки три исхода, не два:** «хорошо», «плохо», **«не смог проверить»**.
  Третий не равен первому. Что с ним делать — решает вызывающий: для своей
  страницы непроверенность блокирует, для чужой — предупреждает.
- **Отказ не глушится.** Пустой `catch` превращает поломку в «данных нет».
  Ловить можно, молчать нельзя: имя проверки и SQLSTATE — в лог.
- **Промпт не требует того, чего нет в данных.** Просить «деталь, которую
  знают не все», не дав источника, — заказ на выдумку. Проси из данных и
  говори прямо: пустая строка лучше придуманной.
- **Ноль результатов при нулевом входе — отказ, а не успех.** Прогон, который
  разобрал 0 из 41, обязан краснеть.

Сторожа этого правила: `sql-interval-not-concatenated`, `post-no-invention`,
`schema-coverage`, `derived-stages`, `cleanup-queue`, `trust-decision`,
`cron-heartbeat-honest`, `funnel-census`, `beacon-check`, `sql-shape-check`,
`sql-param-cast-shape`.

### Объявленный исход без источника (правило 10.09)

**У всего, что объявлено, обязан быть производитель, потребитель и сторож,
который это держит.** Тип, конфиг, докстрока или экран — не механизм; они
лишь обещают его. За два дня, 09–10.09, обещание без исполнения нашлось
четырьмя разными способами:

- **линтер**: подробный `eslint.config.mjs` с обдуманными переопределениями —
  и ни одного вызова ни в CI, ни в pre-commit; 8 ошибок и 309 предупреждений
  три недели невидимы (#1749);
- **тип тревоги `avalanche`**: объявлен в ленте, инструкция для пуша
  написана — а классификатор МЧС его не производил ни разу; предупреждение
  о лавинах уходило как «погода» с советом про ветер (#1763);
- **`aiCodeReview`**: докстрока обещала ручной триггер `type=review` и
  smoke-проверку — тип роут отвергал, функцию не звал никто;
- **проверка деплоя**: единственный признак «это моя сборка» — `built_at`,
  и он ложный; старый образ дважды за час сошёл за свежий (#1762).

Механизм один: **описание живёт дольше кода**, и читающий верит описанию.
Внешний аудит по README такого не видит принципиально — он оценивает
текст. Видят переписи, которые репозиторий делает о себе сам.

Отсюда требования:

- **Новый тип / статус / конфиг заводится вместе с производителем** — в том
  же PR. Тип без производителя — не «задел на будущее», а провод в никуда.
- **Сторож держит связку, а не половину.** `alert-types-produced` требует
  производителя у каждого типа ленты; `lint-runs-in-ci` — вызова линтера;
  `config-has-consumers` — потребителя у каждой секции `lib/config.ts`;
  `field-nav-hard` — жёсткий переход, ПОКА экран в прекэше, и краснеет,
  когда он оттуда уйдёт. Сторож, проверяющий только объявление, зеленеет
  ровно тогда, когда механизм отвалился.
- **Непроизводимое — записывается с причиной, не глушится.** Список
  `KNOWN_UNPRODUCED` в `alert-types-produced` самоустаревающий: появился
  производитель — тест требует убрать запись. Реестр в markdown такого
  не умеет — он сам стал бы объявлением без источника. Тем же устроен
  `KNOWN_UNCONSUMED` в `config-has-consumers`.

**Случай 11.09: конфиг, который никто не читал.** `lib/config.ts` объявлял
четыре блока моделей — `deepseek` (дефолт `deepseek-v4-pro`, а провайдер
выводит его 14.09), `xai` (`grok-4`), `minimax`, `openrouter`
(`llama-3.1-70b`, лето 2024) — и поле `dailyBudget`. Не читал ни один из
них НИКТО: модели резолвятся в `lib/ai/providers.ts` из `/v1/models`, бюджет
считает `/api/cron/llm-budget-check` прямо из `process.env`, мимо конфига.

Мёртвое не ломается — в этом и ловушка. Блок с `apiKey`, `baseUrl`, `model`,
`timeout` выглядит как место, где настраиваются модели, и первый, кому
понадобится их сменить, поменяет здесь. Вдобавок он учит нарушать §8:
захардкоженный id ровно там, где правило требует резолва. Перепись того же
дня: из четырнадцати секций конфига читаются пять — остальные девять в
`KNOWN_UNCONSUMED` с причинами, потому что у каждой причина своя
(`security` и `payments` описывают то, что живёт под §7; `cache` и
`monitoring` — инфраструктуру, которой в платформе нет вовсе).
- **Докстрока, обещающая путь, которого нет, — дефект кода**, а не
  документации. Правится или удаляется вместе с функцией.

### Сторож судит поведение, не текст (решение владельца 13.10)

Три сторожа за один день, 13.10, упёрлись в правку, которая правило не
нарушала: подпись видео на карточке тура, строка оператора на витрине, срез
шапки миграции по слову `BEGIN`. Все три сравнивали не поведение, а ЛИТЕРАЛ
исходника — `toMatch(/<OperatorNameLink name=\{tour\.operator_name\}…/)`.
Такой сторож ловит рефакторинг, а не дефект: краснеет, когда код переписан
верно, и зеленеет, когда компонент стоит в файле, но не рендерится.

Владелец дал карт-бланш: **правило проверяется рендером и данными,
регулярка по исходнику — только для запретов.**

- **Экран, компонент, подпись, ссылка** — рендер (`@testing-library/react`,
  jsdom) с данными и проверка того, что видит человек: текст, `href`,
  `aria-*`, порядок в документе. Тяжёлый экран — вынести проверяемый кусок в
  свой компонент (так появился `components/tours/TourClips`).
- **Правило в функции** — вызов на граничных данных, не поиск строки вызова.
- **SQL, миграция, workflow, конфиг** — сами артефакты; их текст судить
  можно, но по смыслу (гейт, колонка, расписание), а не по форме строки.
- **Регулярка по исходнику — только «этого быть не должно»**: `text-white`
  на сплошном фоне, пустой `catch`, старый адрес, импорт S3-клиента в
  клиентский код, `BEGIN` в миграции.
- **Реестр поверхностей** («на каждой из девяти страниц имя — ссылка») —
  рендер каждой поверхности, а не поиск `<OperatorNameLink` в файле.

Сторож на сторожей: `tests/unit/guards-judge-behavior.test.ts` держит
замороженный список тестов, которые ещё сравнивают JSX-литералы, с числом
вхождений в каждом. Новый такой тест — красный; переписанный на рендер —
список обязан уменьшиться (запись самоустаревает, как `KNOWN_UNPRODUCED`).
Размер долга называет сам сторож, не этот абзац. Первые переписанные —
`catalog-storefront`, `tour-video-clips`, `operator-marketplace-readiness`.

### Случай 24.08: запрос, который не выполнялся никогда

Форма «вставь, если такого ещё нет» — `INSERT INTO t (...) SELECT $1, ...
WHERE NOT EXISTS (... WHERE c = $1)` — отвечает **42P08 «inconsistent types
deduced»**, если у параметра нет якоря типа в списке `SELECT` (тип целевой
колонки туда не доходит), а в сравнении с колонкой якорь есть. Запрос не
выполняется НИКОГДА: не иногда, не под нагрузкой.

Найдено в трёх местах, и цена у всех трёх разная:

- **маяк воронки** (`app/api/funnel/route.ts`) — `funnel_events` пуста с
  момента заведения (миграция 839). Вся середина воронки была не пустой, а
  НЕИЗМЕРЯЕМОЙ, и «никто не трогает форму брони» звучало как факт о
  туристах, будучи фактом о нас;
- **регистрация партнёра** (`app/api/auth/register/route.ts`) и **профиль
  при входе** (`lib/auth/partner-profile.ts`) — профиль не создавался вовсе
  у всех партнёрских ролей, кроме оператора (у того отдельная ветка
  `VALUES`).

**Запертую дверь дал не сам 42P08, а его сочетание с двумя вещами.** В
регистрации не было транзакции: строка в `users` фиксировалась
автокоммитом, дальше падал INSERT профиля, человек получал 500 «попробуйте
позже», а на повторе — 409 «пользователь уже существует», и выйти из этого
не мог ничем. А `catch` не писал в лог НИЧЕГО — поэтому за полтора месяца
никто не увидел ни одной строки об отказе.

Разделение труда между сторожами намеренное:

- приговор выносит **`PREPARE`** на проде (`GET /api/cron/sql-shape-check`):
  вывод типов делается на разборе, до выполнения — ни одной строки не
  вставляется;
- **полноту** реестра держит CI (`tests/unit/sql-param-cast-shape.test.ts`):
  запрос этой формы, не внесённый в реестр, не проходит сборку.

Судить статикой ЗАПРЕЩЕНО, и это проверено на опыте: первая версия сторожа
требовала одинаковое приведение у всех употреблений параметра и пометила
два РАБОЧИХ запроса. В `lib/places/aliases.ts` параметр сравнивается с
`p.id::text`, а вставляется в `place_id` — правильное приведение у двух его
употреблений РАЗНОЕ. Вывод типов повторить статикой нельзя, его делает
сервер.

Живой путь записи отдельно проверяется `GET /api/cron/beacon-check`: тот же
INSERT в транзакции с откатом в `finally` — строка не остаётся по
построению, а не по удаче. Посылать настоящее событие ради диагностики
нельзя: в аналитике навсегда осталось бы выдуманное касание, и следующий
счёт воронки принял бы пробу за туриста.

**Обязательно:**
- TypeScript строгий — `unknown` + type guards, без `any`
- Все API routes — Zod валидация входных данных
- JWT проверка на каждом защищённом маршруте
- SQL — только параметризованный (`$1, $2`), никогда конкатенация
- Ошибки — понятные сообщения на русском
- Никаких эмодзи в коде, UI, логах

**Запрещено:**
- Обращение к таблице, которой нет `CREATE TABLE` в `migrations/` или baseline.
  Схему выводят из этих файлов; чего в них нет — проверить нечем, и ошибка в
  колонке доживает до прода. Замер 19.08: 30 таблиц вне реестра, включая весь
  модуль трансферов, `operators`, `payments`, `payouts` и документы туриста.
  Список заморожен сторожем `tests/unit/schema-coverage.test.ts` и может
  только сокращаться
- `console.log` в продакшн-коде
- Секреты в коде — только `.env.local`
- Изменение схемы БД без SQL-миграции
- `SELECT * FROM kamchatka_routes` — только через `v_kamchatka_routes_api`
- `import pool from` — только `import { pool } from '@/lib/db-pool'`
- `FROM bookings` — только `FROM operator_bookings` (колонка `booking_status`, не `status`)
- `FROM tours` — только `FROM operator_tours` (или `v_kamchatka_routes_api` для публичных маршрутов)
- Несколько запросов разом на одном соединении — `Promise.all` на клиенте открытой транзакции. Соединение их
  параллельно не исполняет: драйвер ставит лишние в свою очередь и в `pg@9` такой вызов уберёт. Запросы на клиенте
  транзакции идут по одному (слово владельца 23.11 — нашлось в расчёте цены брони, `lib/tours/honest-price`).
  Сторожа: `tests/unit/honest-price.test.ts`, блок «цена брони читается по одному запросу» в
  `tests/integration/booking-writers.pg.test.ts`
- `callDeepSeek()` / `callOpenrouter()` напрямую, с `await` и без — только через `callAIWaterfall()` или `callAIFast()`; прямые вызовы — только в `lib/ai/providers.ts` и пробах провайдеров. Список проб с причинами (`PROBES`) и сторож в CI — `tests/unit/ai-direct-calls.test.ts` (#2451); хук `pre-commit` лишь предупреждает раньше. `callMiMo` удалена переписью блока D
