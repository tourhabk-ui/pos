# Денежный путь

Деньги — единственное место, где ошибка стоит туристу или оператору рублей, а
платформе — доверия. Правила ниже выведены из разборов 11.09, 24.09, 25.09 и
аудитов кабинетов (оператор, агент, жильё). Каждое уже было нарушено хотя бы
раз. Первоисточник — `CLAUDE.md` §7; этот файл — рабочий чек-лист к нему.

## 0. Прежде чем трогать

- `app/api/payments/` — зона §7 «НЕ ТРОГАТЬ». Правка приёмника — только по
  явному слову владельца в этой сессии. Нет слова — план и вопрос, не код.
- Прочитать сторожей, которые держат путь (раздел 6), и понять, какой из них
  покраснеет от правки. Если ни один — сторожа не хватает, его пишут первым.

## 1. Порядок: заявка → подтверждение оператора → оплата

- Платится бронь, которую ПОДТВЕРДИЛ оператор. Оплату до подтверждения не
  предлагать и не принимать: `/api/bookings/tour` списывал раньше и удалён.
- Выдача QR/ссылки на оплату статус брони НЕ меняет.
- «Оплачено» — это `paid_at IS NOT NULL`, а не `booking_status = 'confirmed'`.
- Поздний вебхук по отменённой брони не воскрешает её: UPDATE брони в
  приёмнике всегда с условием на допустимые статусы
  (`AND booking_status IN ('confirmed','pending_payment')`).
- Сумма из вебхука сверяется с бронью и платежом (`amountMatches`).

## 2. Книга: `tour_payments`

- Строку HELD пишет ЕДИНСТВЕННАЯ дверь — `holdTourPayment()`
  (`lib/payments/hold-tour-payment.ts`), в той же транзакции, что `paid_at`.
  Своего INSERT в приёмнике быть не должно.
- Срок выплаты оператору — конец тура + 36 ч: `RELEASE_AFTER_SQL`. Никогда
  `release_after = NOW() + ...` — это выплата до тура.
- `ON CONFLICT (cp_transaction_id)` — только с предикатом частичного индекса
  `WHERE cp_transaction_id IS NOT NULL`. Без него 42P10 на ВЫПОЛНЕНИИ, а
  PREPARE проходит — sql-shape-check этого не видит (см. `pg-verify`).
- Таблицы `payments` на проде НЕТ. Код, который идёт в неё первой, падает
  раньше полезной работы.

## 3. Комиссия

- Ставку назначает владелец. `partners.commission_current` не меняет никакой
  автомат (`recalculate_commission` не звать).
- Читать ставку — только `effectiveCommissionPercent()` или
  `COALESCE(p.commission_current, $n)` с `PLATFORM_COMMISSION_PERCENT`.
  `Number(null)` даёт 0 — молча нулевая комиссия.
- Начислять — только `recordCommissionFromBooking()`; каждый роут, пишущий
  `paid_at` броне, обязан её звать (сторож находит приёмники по коду).
- `0` — «комиссии нет», NULL — «не назначена». Не подменять одно другим.

## 4. Выплата

- Оператору: часовой релиз `/api/cron/payouts`, только по НЕотменённой брони
  (`notCancelledBookingSql`). Удержанная часть при поздней отмене оператору
  автоматически не уходит.
- Агенту: одна ставка на агента (`partners.agent_commission_rate`), считает
  одна функция — `lib/payments/agent-commission.ts` (`loadAgentMoney`).
  Начислено — только с оплаченных неотменённых продаж. Ставки нет — сумма
  «не назначена», а не 0. Заявка на выплату и отметка администратора;
  уникальные индексы (миграция 1024) не дают двух открытых заявок и двойной
  выплаты одной продажи.
- Выплата — действие администратора с отметкой, не автомат, пока владелец не
  решил иначе.

## 5. Возврат

- Сумма — `computeTourRefund()` (`lib/payments/tour-refund.ts`) по условиям
  тура: отменил оператор/админ — 100%; нет условий (NULL) — 100%; иначе окно
  `cancellation_free_days` и `cancellation_late_refund_percent` по дате
  Камчатки.
- В транзакции отмены — `recordRefundDue()` пишет `tour_payments.refund_due`.
  Каждая дверь отмены (турист, оператор из кабинета, админ) зовёт его.
- Технического возврата через банк НЕТ. Деньги переводит администратор
  вручную и отмечает через `POST /api/admin/finance/refunds` с причиной
  (≥ 8 символов, номер операции). Ни оператору, ни владельцу жилья не
  поручать «перевести вручную» — денег у них нет, они у платформы.
- Возврат — только по ОТМЕНЁННОЙ брони (`cancelledBookingSql`).

## 7. Новый вид брони (жильё, трансфер, снаряжение)

Своего денежного пути НЕ изобретать. Вопросы владельцу до кода:
1. Кто принимает деньги — платформа или сам исполнитель?
2. Если платформа: книга как `tour_payments`, комиссия, срок и способ выплаты.
3. Подтверждение до оплаты — да (по умолчанию, как у туров).
4. Возврат — по чьим условиям и кто его отмечает.

Пока ответов нет — честно: «оплата на месте / по договорённости», без кнопки
«Оплатить» и без обещания ссылки на оплату. Аудит жилья 26.09 нашёл ровно
обратное: кнопка есть, платёж создаться не может, возврат поручен владельцу.
