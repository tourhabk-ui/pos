## 0. Рамка

**Решение в одной фразе:** `/planning?mode=trail` перестаёт быть «страницей со всем» и становится
одним контуром: **Трек → Паспорт → Потребности → Брифинг → Кокпит → Восстановление**.
Мы не переделываем страницу «красивее» — мы делаем уже существующую инженерную честность
(fidelity, dataConflict, off-track по точности GPS, офлайн-коридор) видимой и связной.

**Непереговорные критерии качества** (принимаются как definition of done всего плана):

1. **Zero false-ready** — частичный/непроверенный офлайн-пакет никогда не выглядит готовым.
2. **No false geometry** — `sketch`, `points_only`, `dataConflict` не получают точный прогресс/ETA/«вернитесь на трек» как у снятого трека.
3. **No safety theatre** — нет «безопасно идти», медицинских оценок, общего safety-score; «4 из 7» — статус подготовки доменов, не разрешение.
4. **Field focus** — в активном режиме только полевые действия: Карта, Условия, Группа, SOS.
5. **Graceful degradation** — у каждого сенсора/карты/сети есть ясное «что работает / что нет / что сделать».
6. **Real field evidence** — громкие заявления только после device matrix и полевых сессий.

## 3. Принятые архитектурные решения

### 3.1 Паспорт маршрута (Route Passport v0) — вычисляемый контракт, а не новая таблица

Имя `route_passport` в БД занято OCR-таблицей (`route_passport_ocr`, миграция 730 — PDF с visitkamchatka).
Поэтому «полевой паспорт» — это **расширение ответа `/api/routes/[id]` полем `passport`**, собранным
детерминированно из уже существующих данных:

```
passport: {
  grade:        'surveyed' | 'sketch' | 'points_only' | 'unknown',  // из trackLine(coords, geometry->>'source')
  source:       string | null,        // geometry->>'source' (idilesom/osm/gpx/waypoints_synthetic/…)
  version:      number,               // НОВОЕ: kamchatka_routes.route_version
  waypoints:    number,
  observedAt:   string | null,        // passport_verified_at / updated_at
  access: { mchsRequired, mchsPhone, parkName, parkApprovalUrl },
  officialPassportUrl: string | null
}
```

Единственная миграция для v0 — **`863_route_version.sql`**: `route_version INT NOT NULL DEFAULT 1`
в `kamchatka_routes` + инкремент во всех код-путях, пишущих `geometry` или `route_waypoints`
(найти грепом на этапе 1; при пропуске пути версия просто не поднимется — деградация мягкая).
`geometry_grade` в колонку **не дублируем**: грейд всегда выводится из источника + плотности
одним модулем (`line-standard`), чтобы не появился второй источник истины.
`segment_confidence[]`, `review_owner`, `exit_points[]` из концепции — сознательно отложены (см. §7).

### 3.2 Field Pack — атомарный manifest в IndexedDB

Сейчас готовность пакета размазана: тайлы в Cache Storage, запись о карте в `localStorage`,
маршруты в IndexedDB, safety-снимка нет. Вводим **`FieldPackManifest`** (store `fieldPacks`
в существующей БД `kamchatour-offline`, bump версии схемы):

- ассеты: `tiles`, `route`, `waypoints`, `safety_snapshot` — каждый со статусом `ready | partial | missing | stale`, `expected/present`;
- привязка к `routeId + routeVersion` (version pinning);
- `storage: { persistent, estimatedBytes }`;
- **готов к полю** = `route` и `waypoints` ready, карта ready **или** пользователь явно принял «без карты»; `partial` никогда не отображается зелёным;
- `safety_snapshot` может быть stale — но его возраст обязателен на экране («данные 14 мин назад» из макета);
- проверка фактического наличия тайлов — sample-проверкой Cache Storage при сборке manifest, не только по метаданным.

Запись `saved-map` переезжает из `localStorage` в manifest с обратной совместимостью чтения.
Кнопка из макета «Сохранить полевой пакет» — один шаг (карта + точки + snapshot), а не три.

### 3.3 Прогресс — только честный (макеты 1–2)

Реализуем блок «Маршрут 46% · Пройдено 5,7 из 12,4 км · осталось 6,7 км» как отдельный слой
под дистанцией до точки, по таблице инвариантов из концепции:

| Состояние | Показ |
|---|---|
| surveyed + свежий GPS | полный distance progress по **треку** (через `distanceAlongTrack`), bar `--success` |
| GPS stale | последний прогресс, приглушён, с временем фикса; bar не анимируется |
| off-route на треке | прогресс заморожен; «вне трека» не добавляется в «пройдено» |
| sketch | только checkpoint progress («точка 3 из 7»); километраж — лишь как «ориентир между точками» |
| points_only / unknown | только «точка N из M» + bearing; ни процентов, ни общего километража |
| dataConflict | ни прогресса, ни ETA — объяснение источников (уже есть) |
| один waypoint | цель и дистанция; без «1 из 1» и бара |

### 3.4 «Подготовка к походу» — детерминированный план, AI только объясняет

Новый экран (макет 3) с моделью из концепции: **7 доменов** (маршрут и доступ / условия и время /
навигация и питание телефона / вода и питание / одежда и укрытие / безопасность-связь-группа /
логистика), «Нужно решить до выхода» (2–4 действия) + «Уже готово».

Миграции **`864_trip_preparation.sql`** (+ при необходимости 865): `trip_preparation_plans`,
`trip_preparation_items`, `trip_preparation_events`; `trip_preparation_shares` — на этапе 5.
Anonymous-first: план живёт на `session_id`/локально, регистрация нужна только для share/хранения.

Правила безопасности модели:
- `required` — только из проверяемого источника (правило маршрута, факт manifest, выбранный сценарий). **«Обязательно по мнению AI» не существует.**
- у каждого item — `reason` и `source` (`route_passport | field_pack | official_rule | condition_snapshot | user_input | ai_suggestion`);
- item «Сохранить полевой пакет» получает состояние **из manifest по факту**, не по клику;
- партнёрские предложения — только после выбора «арендую/нужен совет», не влияют на importance;
- медицинские данные не собираются; приватная заметка — локально, в share не входит.

`/tools/equipment` не удаляется: rate-limit сразу (этап 0), затем deep-link и превращение
в вкладку «Снаряжение» плана с ownership-состояниями (есть / возьму / арендую / решить / не применимо).

### 3.5 Дизайн: «стекло для контекста, непрозрачность для действия»

**Решение владельца 2026-08-15: стекло разрешено** как полноценный элемент языка (зафиксировано
в CLAUDE.md §2, `.claude/DESIGN_SYSTEM.md` §3 и скилле `vedar-design` §5). Для этого контура:

- Базовый вид «Подготовки к походу» — **стеклянный макет №4**: под экраном рельефная/фото
  подложка; стеклом — шапка маршрута, статус доменов и фоновые слои. **Карточки «Нужно решить
  до выхода» — плотные** (`bg-black/60` и выше, вплоть до непрозрачных): это действия, а по
  контракту «стекло — для контекста, непрозрачность — для действия» самое важное на экране
  не платит за красоту контрастом (правка принята владельцем 2026-08-15). Тёмный solid-макет №3
  остаётся фолбэком для `prefers-reduced-transparency` и слабых устройств — layout и смысл
  идентичны, blur выключается.
- Field Cockpit — стекло дозированно: полупрозрачными могут быть статус-строка и контекст поверх
  карты/рельефа; **компас, главная цифра дистанции, SOS, offline-warning, confirmation — всегда
  непрозрачные приборы** (граница закреплена в правиле владельца).
- Подложки стекла — только чёрная/белая альфа или CSS-токены, не хардкод-hex. Новые токены
  концепции (`--glass-mist`, `--glass-deep` и т.п.) заводим в `globals.css` на этапе 3/4, только
  если альфа-варианты окажутся недостаточными — отдельным мелким PR, не россыпью по компонентам.
- Цвета — существующие токены: подтверждено `--success`, «нужно решить» `--warning`,
  SOS `--danger`, данные `--ocean`. Иконки lucide, заголовки Playfair, без эмодзи и `@keyframes`.
- SOS в кокпите — через общий `components/shared/EmergencyAction.tsx`-контур (CLAUDE.md §7, урок #887),
  не собственная кнопка. Текущий `tel:112` в `OnTrailTab` привести к общему компоненту на этапе 3.
- Частные стандарты со сторожами (карточка тура: стекло только в герое) не трогаем — они
  меняются отдельными решениями владельца.

### 3.6 Один полевой экран

`app/on-route/` объявляется устаревшим: после сверки функциональности (что из 411 строк
не покрыто `OnTrailTab`) — redirect на `/planning?mode=trail`, удаление из `OFFLINE_CAPABLE_ROUTES`.
Вторая карточка тура уже научила: копии расходятся.

### Этап 1 — Паспорт маршрута на входе (P0)

1. Миграция `863_route_version.sql`; инкремент версии в код-путях записи geometry/waypoints.
2. `/api/routes/[id]` отдаёт `passport` (§3.1). Модуль сборки — `lib/routes/passport.ts` (использует `line-standard`, не дублирует).
3. Модалка выбора в планере: бейдж типа **«Трек / Набросок / Точки»** на каждом элементе списка и в превью; место (kind=place) не может зафиксироваться как полевой маршрут.
4. CTA меняет формулировку: «Открыть навигатор» (surveyed) / «Открыть ориентирование» (sketch/points) — без блокировки, с объяснением предела данных.
5. Хрупкость двух таблиц (находка 8): оба эндпоинта выбора должны отдавать id, гарантированно разрешимый в `/api/routes/[id]`; проверить пересечение id `agent_route_knowledge` ↔ `kamchatka_routes` и закрепить тестом.

Готово, когда: пользователь до фиксации маршрута видит тип линии, источник и версию; place не запускает field mode.

### Этап 2 — Field Pack manifest (P0/P1)

1. `lib/offline/field-pack.ts`: `FieldPackManifest`, сборка, верификация (sample Cache Storage), статусы по ассетам.
2. IndexedDB store `fieldPacks` (bump версии `kamchatour-offline`); миграция чтения `saved-map` из localStorage.
3. `safety_snapshot` кэшируется при сборке пакета; возраст всегда на экране.
4. UI «Сохранить полевой пакет» — один шаг; чек-лист готовности: Карта / Трек и точки / Условия / Группа — начало Field Briefing v1 (scrollable, без блокировки, с ценой пропуска). Без счётчика шагов «2/3» в шапке — прогресс-бюрократия противоречит «не блокировать» (правка принята владельцем 2026-08-15); показывается состояние слоёв, не пройденность анкеты.

Готово, когда: в авиарежиме пакет открывается; partial нигде не зелёный; сторож-тест на manifest (расширение `offline-crumbs-saved-map.test.ts`).

### Этап 3 — Field Cockpit (макеты 1–2)

Иерархия сверху вниз (по макету): статус-строка (`GPS ±8 м · название · 3 из 7` + «Карта сохранена · данные N мин назад») → **компас** с «На точку: 042°» → **1,8 км до следующей точки** → чипы (тип точки · ~время · +набор высоты) → **прогресс-бар** (§3.3) → **trust card** «Снятый трек · линия проверена» / честные варианты для sketch/points/conflict, с раскрытием «Показать качество данных» (fidelity + pack + возраст snapshot + качество фикса = data-trust-engine v0) → четыре кнопки **Карта / Условия / Группа / SOS**.

Инженерно:
1. Вынос `OnTrailTab` из `_PlanningClient.tsx` в `components/field/` по кускам (компас, прогресс, trust card, действия) — вместе с фичей, не big-bang; каждая вырезка накрыта существующими сторожами.
2. SOS через общий контур `EmergencyAction` (§3.5).
3. «Условия» — внутренний снимок из пакета с возрастом и источником, не внешняя ссылка на погоду.
4. `?mode=trail` двусторонний deep-link (URL обновляется при переключении таба).
5. `/on-route` → redirect (§3.6).

Готово, когда: иерархия работает на реальном GPS; все строки таблицы §3.3 воспроизведены тестами (stale, sketch, points_only, conflict, off-route); компас не главный источник истины при `unconfirmed`.

### Этап 4 — «Подготовка к походу» (макет 3)

1. Миграция `864_trip_preparation.sql` (plans/items/events; идемпотентная, по стандарту).
2. `lib/preparation/` — движок правил v1 (детерминированный, версия правил в коде), модель item (§3.4).
3. Экран (вход из превью маршрута в планере и с карточки маршрута `/routes/[id]`): шапка «маршрут · дата · день/группа/ночёвка», «N из 7 доменов подготовлены», «Нужно решить до выхода» (2–4 карточки с действием), «Уже готово», табы Обзор/Снаряжение/Группа/Пакет.
   Правила для «N из 7» (правка принята владельцем 2026-08-15 — число прочтут как разрешение,
   сколько бы оговорок рядом ни стояло): слово всегда «подготовлены», никогда «готов к выходу»;
   при 7/7 сегменты не сливаются в одну зелёную полосу и зелёной галочки на весь экран нет;
   если метрики покажут, что 7/7 отучает пересматривать условия, — число убирается, остаётся
   список действий.
4. Четыре вопроса (длительность / группа / опыт / что уже есть) — прогрессивно.
5. Интеграции: item «полевой пакет» ← manifest (этап 2); «регистрация МЧС» ← `mchs_registration_required` + `MCHS_ONLINE_FORM_URL`; «трансфер» — manual_confirm; «briefing» — заготовка под этап 5.
6. `/tools/equipment` → deep-link во вкладку «Снаряжение»; ownership-состояния; AI-ответ размечается как `ai_suggestion` и не может дать `required`.
7. **Единственность поверхности подготовки** (правка принята владельцем 2026-08-15): чек-лист
   подготовки в `PlanningTab` не сосуществует с новым экраном — он становится входом в него
   либо умирает. Две поверхности подготовки — та же болезнь, что две карточки тура и две
   SOS-кнопки (#887): копии расходятся. Сторож на единственность — вместе с экраном.

Готово, когда: пользователь за 10 секунд называет следующее действие и почему; план переживает перезагрузку; Зod-валидация и авторизация на всех новых API.

### Этап 5 — Группа и брифинг (P1)

Share-объект (scoped, expiring): маршрут + версия, старт/финиш, плановое возвращение, контакт, состояние пакета — **без** live-location по умолчанию и без обещаний «группа наблюдает» офлайн («последняя передача: время»). Миграция `trip_preparation_shares`. Отправка briefing контакту = карточка из макета.

### Этап 6 — Recovery как состояния (P1)

Оформить существующую математику в state-based карточки (не popup): off-route на треке («Вы примерно в N м от линии» + пунктир возврата — connectorLine, честное имя), sketch («подтверждённой линии нет» — без «вернитесь на трек»), stale GPS (заморозка цифр + timestamp), dataConflict (карта и ориентиры, без precision-метрик), карта не готова (координаты + компас). Три действия: вернуться к линии / продолжить намеренно / изменить план. Никакого автоперестроения пути.

## 6. Метрики

North Star — **Prepared Field Session (PFS)**: выбран навигационно пригодный объект → открыт паспорт → route/waypoints готовы, offline-state подтверждён или осознанно ограничен → открыт кокпит или отправлен briefing.

Старт — с трёх-четырёх событий без координат и ПД (D1-гард): `field_pack_state`
(ready/partial/missing по ассетам), `field_cockpit_opened`, `recovery_opened`, при появлении
экрана подготовки — `needs_action_plan_created`. Полная воронка (`route_type_seen`,
`field_briefing_opened`, `field_sensor_state`, `briefing_shared`, completion-метрики) — только
когда будет кому смотреть на дашборд: строить восемь событий поверх 152-ФЗ-гардов сейчас —
аналитический театр (правка принята владельцем 2026-08-15). Телеметрия privacy-respecting,
без фоновой слежки.

## 7. Что сознательно НЕ делаем сейчас

- Native shell / background GPS — только после device matrix и подтверждённых отвалов (gate из дорожной карты).
- Интеграции спутниковых устройств (inReach/Zoleo), обещания спутникового SOS — телефонная PWA маяком не является; SOS остаётся 112 + офлайн-очередь.
- `segment_confidence[]`, review workflow, verified-route programme, route passport API/MCP наружу — горизонт 3.
- Соцлента, новые map layers, расширение каталога/географии, новый «движок подбора» (CLAUDE.md §4).
- Glass-редизайн поверхностей вне этого контура (каталог, карточка тура, ЛК) — стекло теперь разрешено (§3.5), но перекраска чужих экранов в этот план не входит; каждая поверхность — отдельным решением.
- Общий safety-score, медицинские оценки, «безопасно идти».

## 9. Порядок и объём

Последовательность жёсткая: **0 → 1 → 2 → 3 → 4**, затем 5 и 6 (можно параллельно).
Этап 0 — серия мелких независимых PR (низкий риск, быстрый мерж). Этапы 1–2 — фундамент данных,
без них кокпит и подготовка «врут». Этап 3 и 4 — видимые пользователю макеты; каждый
самостоятельно шиппится. Ориентир из дорожной карты — шестинедельный цикл:
нед. 1–2 = этапы 0–1, нед. 2–3 = этап 2, нед. 3–4 = этап 3, нед. 4–5 = этап 4, нед. 5–6 = этапы 5–6
и первые структурированные полевые сессии (авиарежим, слабая сеть, разные устройства).

Первый шаг после утверждения плана: PR этапа 0.1–0.4 (четыре честности фундамента) — они
не требуют ни одного продуктового решения и снижают риск всем последующим этапам.
