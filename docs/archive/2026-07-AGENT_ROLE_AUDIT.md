# Аудит роли «Турагент» (`agent`) и план

> Статус: аудит завершён (июль 2026). Решение владельца: **сначала аудит-док +
> редизайн кабинета; деньги/воронку комиссий не трогать до отдельного «го».**
> Этот документ — источник правды по находкам и плану.

## 1. Что за роль

| Аспект | Значение | Где |
|--------|----------|-----|
| id роли | `agent` (партнёрская, наравне с operator/guide/transfer/stay/gear) | `types/index.ts`, `lib/auth/role-switch.ts` |
| Описание | «Управление группами, ваучерами и партнёрствами» | `app/api/roles/route.ts:135` |
| Кабинет | `/hub/agent` | `lib/auth/role-routes.ts:13` |
| Гейтинг | `requireAgent` = роль ∈ {agent, admin} | `lib/auth/middleware.ts:82` |
| Заявленные права | manage_groups, manage_vouchers, view_commissions, manage_partnerships, view_analytics, gds_integration | `app/api/roles/route.ts` |

**Суть роли:** B2B-посредник (турагент/агентство) — приводит клиентов и группы,
оформляет брони на туры операторов, ведёт ваучеры, получает комиссии/выплаты,
работает по реферальной программе.

Кабинет (11 страниц): обзор · bookings · clients · commissions · find · leads ·
referral · stats · vouchers · profile · onboarding. Все страницы живые (реальные
API + `requireAgent` + Zod), но сделаны **до** «туристского формата».

## 2. Находки

### 🔴 F1. Двойная воронка комиссий (главное)

Существуют ДВА параллельных механизма комиссий, которые противоречат по честности:

**Силос A — legacy, самодекларируемый (`agent_bookings` + `agent_commissions`)**
- Агент **вручную** вбивает «бронь» в форму (`POST /api/agent/bookings`): сам задаёт
  цену, хардкод-ставка 10% → `INSERT agent_bookings` + `INSERT agent_commissions`
  (`app/api/agent/bookings/route.ts:197,215`).
- **Оторван от реальных `operator_bookings`**: нет реальной брони у оператора, нет
  слота, нет оплаты. Комиссия начисляется на самодекларированную сумму.
- Дашборд/`stats`/`commissions` читают ИМЕННО этот силос → агент может **выдумать
  выручку и запросить реальную выплату** (`request-payout` → `commission_payouts`).
- FK `agent_bookings.tour_id → tours(id)` — **запрещённая §4 таблица** (легаси).

**Силос B — честный (`agent_referral_links` + `operator_bookings.referral_link_id`)**
- Миграция `727_operator_bookings_referral.sql`. Агент делает реф-ссылку → турист
  бронирует через реальный `POST /api/bookings/tour` → атрибуция в
  `operator_bookings.referral_link_id`.
- Заработок считается **живо** только с оплаченных: `payment_status='paid'`
  (`app/api/hub/agent/referral/route.ts`). Это правильный путь (PR #78).

> **Вывод:** главные денежные цифры кабинета берутся из самодекларируемого силоса A,
> а рядом уже есть честный силос B на реальных оплаченных бронях. Для платформы
> «не врать» — это ядро проблемы и вектор фрода. **Решение отложено владельцем.**

### 🟠 F2. Матрица прав декоративна
`manage_partnerships`, `gds_integration`, `manage_vouchers`, `view_commissions`,
`manage_groups` встречаются ТОЛЬКО строками в `app/api/roles/route.ts` — нигде не
enforce'ятся (`hasPermission`/checkPermission отсутствуют). Гейтинг грубый,
ролевой. Обещанные ролью фичи (GDS-интеграция, партнёрства) **не реализованы** —
это ярлыки. Отдельной таблицы прав нет.

### 🟡 F3. Дубль подбора туров
`find` (`/api/agent/find-tours`, на `operator_tours`) и `agent-market` — два входа
в подбор. Свести к одному.

### 🟡 F4. Кабинет вне «туристского формата»
11 страниц живые, но визуально старые: нет playfair-хедера, StatChip-сводки,
icon-circle секций, Loader2 — расходятся с эталоном (`_ModelsClient`,
health-дашборд, дашборд агентов).

## 3. План (фазами, каждая — мержимый PR)

Порядок: доверие → честность → редизайн → удаление легаси. **Фазы 1-2 — сейчас
(аудит-док + редизайн). Фазы 3+ — после отдельного «го» по воронке.**

- **Фаза 1 (этот PR) — аудит-док.** Зафиксировать находки и план (этот файл).
- **Фаза 2 — редизайн кабинета в туристском формате.** Обзор → StatChip-сводка +
  секции-карточки; затем bookings/clients/commissions/referral/vouchers по одной.
  Цифры не менять — только форма. Честные пустые состояния вместо нулей-плейсхолдеров.
- **Фаза 3 (после «го») — честная воронка.** Одно из решений владельца:
  единая на `operator_bookings` (комиссия только с оплаченных) ИЛИ `agent_bookings`
  разжаловать в CRM-черновик без выплат. Убрать самодекларируемые выплаты.
- **Фаза 4 — права по-настоящему** (если нужно): либо реализовать заявленные
  фичи, либо убрать необеспеченные ярлыки из описания роли (не обещать GDS/партнёрства,
  которых нет).
- **Фаза 5 — чистка легаси:** FK `tours(id)` → `operator_tours`/удалить; свести
  дубль подбора; удалить мёртвое по инвентаризации.

## 4. Реферальные ресурсы (что нужно, чтобы программа была «настоящей»)

- **Атрибуция:** `operator_bookings.referral_link_id` (есть, миг. 727). Проверить
  покрытие: ставится ли `referral_link_id` во ВСЕХ путях брони (вебхуки/OCTO/корзина),
  а не только `POST /api/bookings/tour`.
- **Честный заработок:** только `payment_status='paid'` (есть). Отражать
  отдельно: клики → конверсии (атрибутированные) → оплаченные → заработок.
- **Выплаты:** единый источник — из силоса B, не из самодекларации A.
- **Материалы агенту:** готовые реф-ссылки/QR на туры и маршруты, баннеры из
  `public/images/` (Камчатка, не сток), краткий how-to. Только реальные ссылки.
- **Прозрачность оператору:** оператор видит, что бронь пришла от агента X (доверие,
  не скрытая комиссия).

## 5. Несгораемое
- Не менять денежные цифры в фазах 1-2 (только форма/честные пустые состояния).
- API-пути и URL страниц кабинета не двигать.
- Любая правка воронки/выплат — отдельным PR после явного «го» владельца.
